# 社区垃圾投放行为分群

栖梧社区环境运营组按点位和时段采集匿名合计，用分群找出投放行为相近的点位，派发有针对性的宣教，在同址同时段复测，并把未达标点位交给现场班组整改。

## 使用场景

栖梧社区环境运营组负责银杏里、云岫苑和溪径坊的六个投放点。巡查员过去在值班表里记录投放次数、分类正确次数和满溢次数，运营人员分别核对物业发来的点位变更消息，再手工挑选宣教点位。旧址数据容易被带到新址，样本不足时缺少统一的发布门槛，宣教前后的观察时段也经常不同。

上游为巡查员的现场匿名计数与物业的迁移核验，社区运营使用本项目管理点位地址、冻结分析口径并审核宣教，下游由社区联络查看任务结论并安排通知。

| 岗位 | 演示账号 | 页面和权限 |
|---|---|---|
| 巡查员 `analyst` | `field` | 录入匿名窗口、申请地址迁移、提交分群、登记宣教与复测、上报现场条件、排班与登记整改回执 |
| 社区运营 `admin` | `ops` | 巡查员权限、登记点位、确认或撤销迁移、发布分群与归档复测、签核现场条件、派发群组整改、确认旧址停止及结案、读取审计 |
| 社区联络 `viewer` | `desk` | 查看点位、采样流水、运行记录、宣教结果、排班与整改状态 |

三个演示账号的密码均为 `qiwu-demo`。页面状态与后端校验使用同一组角色。

## 演示流程

1. 11 月 10 日早间巡查记录银杏西门计数 `22 次 / 正确 12 / 满溢 1`。11 月 11 日晚间的基线是 `38 次 / 正确 22 / 满溢 3`。这批数据在启动时入账。
2. 巡查员在溪径花厅登记围挡导致的拟迁移地址。按 11 月 10 日至 11 日请求分群，运行暂停并标出 `QW-05`。
3. 社区运营在点位档案确认围挡已拆除，撤销迁移申请。银杏西门补录 11 月 10 日午间 `10 次 / 正确 7 / 满溢 0`。
4. 巡查员按同两日提交三群分析。worker 计算易混投、满溢较多、稳定投放三组画像。只选 11 月 10 日则会因多个点低于样本门槛而暂停。
5. 社区运营复核后派发四张宣教单。银杏西门任务聚焦晚间分类准确率，云岫车棚任务聚焦早间满溢。
6. 11 月 12 日在银杏西门张贴示意图并做桶前示范。巡查员登记执行记录。
7. 11 月 13 日和 14 日晚间分别录入 `15 次 / 正确 14 / 满溢 0`。社区运营归档，晚间正确率由 57.9% 升至 93.3%。
8. 社区联络查看复测结论，沿用银杏西门的桶前指引。低于改善门槛的任务留在需跟进状态。

## 计算与口径

- **采样窗口。** 一条记录对应一个地址版本、日期和时段。时段按上海时间记录，早间 06:00–10:00，午间 11:00–14:00，晚间 17:00–21:00。每次投放记一次观察。正确数是分类符合要求的观察数，满溢记录数是观察时出现满溢的次数。单窗口最少 5 次观察，只接收合计字段。
- **运行闸门。** 分群使用基线区间内、当前地址版本的匿名窗口。所有在册点位均须达到 30 次观察和两个窗口，存在待核迁移即暂停。地址核验通过后，从确认次日起采新址样本。旧址流水保留。分析和确认前复查同一份源数据，哈希变化时暂停。
- **层次聚类。** Python 按点位计算 `正确数/观察数`、`晚间观察数/观察数` 和 `满溢记录/观察数`。三列用总体标准差做 z-score，零方差列置零。以欧氏距离和平均链接计算完整凝聚树，可切成 2–4 群。等距离按固定点位编号顺序决胜，输入快照和 SHA-256 保留计算依据。群组画像为成员特征的等权均值，观察量为成员样本合计。
- **宣教。** 点位正确率低于 80% 时派分类指引，正确率达到 80% 且满溢发生率达到 8% 时派错峰引导。以错误或满溢记录最多的时段为复测时段，相同记录量时优先观察量较大的时段，再按固定的时段代码顺序决胜。点位同时最多一张进行中的宣教任务。
- **复测。** 宣教日期须晚于基线结束，允许补登实际执行日。复测在宣教次日及以后、同址同段采集，至少两个日期且累计 20 次。正确率上升至少 5 个百分点或满溢发生率下降至少 3 个百分点判为已改善。复测为运营描述性比较。

## 启动

```bash
cp .env.example .env
docker compose up --build -d --wait
docker compose exec backend python -m scripts.seed_demo
```

| 入口 | 地址或连接 |
|---|---|
| Web 工作台 | `http://127.0.0.1:18255` |
| FastAPI OpenAPI | `http://127.0.0.1:19255/docs` |
| MySQL 8.0 | `127.0.0.1:17755` / `sorting_field` / `sorting_ops` |

`.env` 支持覆盖三组端口、Compose 项目名、`MYSQL_PASSWORD`、`MYSQL_ROOT_PASSWORD`、`JWT_SECRET` 与 `SEED_DEMO`。演示优先使用回环地址。`SEED_DEMO=true` 时后端启动自动补齐演示档案，后续运行 seed 可保留全部人工操作。`SEED_DEMO=false` 适合由部署方初始化账号和业务数据的环境。常规停止运行 `docker compose down`，重置演示数据运行 `docker compose down -v`。

| 部分 | 实现 |
|---|---|
| 浏览器 | 原生 HTML/CSS/JS、ES modules、Nginx `/api/` 反代 |
| API | Python 3.11、FastAPI、PyMySQL、JWT 会话、事务审计 |
| 队列和 worker | MySQL 持久化运行记录，独立 Python worker 处理排队分群并发出心跳 |
| 数据与登录保护 | MySQL 8.0 持久化业务；Redis 7 提供登录限速 |

开发时用 `docker compose up --build -d` 重新构建受影响服务。`backend/schema.sql` 在 MySQL 创建数据卷时初始化。`backend/src/fieldwork.py` 管点位和采样，`runs.py` / `clustering.py` 管分析快照和计算，`outreach.py` 管任务审批与复测。`frontend/src/pages/` 含各业务工作页。后端启动时按编号补建 `backend/migrations/` 中的新增表，可在已有数据卷上执行。

前后端共享枚举定义位于 `backend/src/contracts.py` 与 `frontend/src/state.js`。MySQL 的角色、采样时段、分群状态和宣教状态约束位于 `backend/schema.sql`。前端使用 `ui.js` 的共用计数、标签、表单和空态组件，业务请求由 `api.js` 管理。

验收资料位于工作区 `test-artifacts/gb-1056/`。项目使用工作区统一的许可约定。


## 采样复核和满溢清运

巡查员提交基线采样争议，另一位运营账号可排除或保留。处于复核中的窗口暂停对应期间分群，排除后从后续基线剔除窗口并重算样本门槛，已确认报告保留原输入快照。

有效窗口同时达到 3 次满溢和 15% 满溢率时，巡查员可按窗口申请清运。运营登记班组与交接安排后，巡查员记录完成结果。清运工单保留原点位、日期和计数依据。


## 现场条件、复测排班和群组整改

- 从采样流水打开「现场条件」，巡查员可记录降雨、通道、标识或值守变化。另一位运营人员核实后，可在对应任务的群组整改中引用该记录。现场条件留在采样窗口上，已确认的分群快照仍按原计数展示。需要排除计数时使用「采样复核」。
- 在宣教执行记录下选择「安排同址复测」，为同址同时段预留宣教后 21 天内的两个日期。首班已入账时可改约未完成的班次，班次入口会填入已约日期。已预约的窗口只能归入对应宣教任务，未排班的任务仍可按原规则录入。
- 运营在「群组整改」选择未达标任务，查看其目标时段的基线、复测和已签核现场条件。系统纳入同次运行、同群、同目标且仍在原址的未派发点位。分类正确率任务可更换标识或安排分拣示范，满溢任务可调整投放时段或指引至备用点位。
- 巡查员逐点记录现场结果。确认迁移的旧址由运营登记停止执行。全部点位有回执后，运营签署结案。整改回执记录现场动作，宣教效果仍以任务中已归档的复测数据为准。
